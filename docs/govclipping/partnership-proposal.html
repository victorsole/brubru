Integration options

Recommended: MCP Plugin (lowest friction)

Brubru as an MCP server that GovClipping's AI agents call directly. Since GovClipping already supports MCP, integration is plug-and-play. No custom API work, no frontend changes on GovClipping's side.

Tools exposed: search_eu_legislation, query_knowledge_base, get_procedure_status, get_calendar_events, search_eprs

Option 2: REST API

GovClipping calls Brubru endpoints from their backend. Standard HTTP, JSON responses. More control, more integration work.

Endpoints: /api/chat, /api/legislative-train, /api/eu-calendar, /api/eprs

Option 3: Embedded widget

Brubru chat widget (iframe or web component) embedded in GovClipping UI. Their users ask EU questions without leaving the platform.

Option 4: Mutual data exchange

Two-way: Brubru provides EU legislative data, GovClipping provides Spanish transposition data. Both products become more complete.

Growth path

Start with MCP (week 1). Add API for custom features (month 1). Add widget for end-user access (month 2). Explore data exchange (quarter 2).

The frame that wins

Brubru is GovClipping's EU-level complement, not a competitor.

  • GovClipping covers the Spanish output side: BOE, BOA, BOP, BOPA, 20 ministries × 17 autonomous communities × parliamentary initiatives × public organisms (AEAT, AEPD, CNMC, CNMV, AIReF, INCIBE, IDAE, OEPM, SEPI, Red.es).
  • Brubru covers the EU input side: where Spanish regulation originates, where it's going, who's steering it, when it forces transposition, whether Madrid is aligned with Brussels.
  • ~70% of Spanish legislation is downstream of EU. Jordi is today flying blind upstream.

Three demos (20 minutes total)

  1. Demo 1 — "The EU origin of today's BOE" (6 min)
    1. GovClipping: pick any recent BOE transposing an EU directive (digital, energy, chemicals, data protection).
    2. Brubru: POST /api/v1/legal-text/resolve-aliases with the decree title or preamble → returns CELEX of the parent EU regulation.
    3. Brubru: GET /api/v1/laws/{celex}/text?format=plain → full EU text (verified on GDPR: 351 KB via EUR-Lex Cellar).
    4. Brubru: GET /api/v1/procedures?q=<topic> → OEIL procedure status.
    Your BOE monitoring + our EU context = end-to-end transposition tracking in one workflow.
  2. Demo 2 — "Is Madrid ahead or behind Brussels?" (6 min)
    1. GovClipping: Spanish government announcement (Ejecutivo module).
    2. Brubru: GET /api/v1/knowledge-guides?q=<topic> → curated guide on EU obligations/deadlines (147 guides).
    3. Brubru: GET /api/v1/calendar/events?institution=EP&committee=LIBE&limit=5 → upcoming EP discussions.
    4. Brubru: GET /api/v1/predictions/{ref}/timeline → XGBoost forecast for when the EU rule finishes.
    See what Brussels is doing next, right beside what Madrid did today.
  3. Demo 3 — "Stakeholder intelligence across borders" (6 min)
    1. GovClipping: "Participación Ciudadana" shows Spanish consultations.
    2. Brubru: GET /api/v1/consultations/by-initiative/13174/feedback → Have Your Say stakeholder data grouped by country, user_type, organisation, Transparency Register number.
    For any Spanish consultation, we show who's pushing back at EU level — and from which country and sector. GovClipping has no access to this layer.

Hola Jordi,

Moltíssimes gràcies pel repàs tan detallat de l'API. És exactament el tipus de feedback que ens ajuda a fer-la apta per a integracions serioses, i he dedicat avui dilluns tot el dia a arreglar-ho.

Avui (dilluns 20 d'abril) — desplegat a producció:

  1. Laws — ara retorna 422 amb reason_code: conflicting_params quan s'envien published_to i published_end amb valors diferents, i 422 amb reason_code: invalid_date_range quan el rang és invertit. He aclarit la descripció OpenAPI de cada paràmetre: published_to és el nom preferit (límit superior, date ≤ valor); published_end és simplement un àlies del mateix bound, existent per compatibilitat amb la vostra API. Si passes tots dos amb el mateix valor, endavant; si els passes amb valors diferents, ara et diem exactament quin és el problema.
  2. MEPs — tota la ruta reescrita. Ara crida directament l'EP Open Data REST v2 (no el SPARQL antic). full_name sempre ve poblat, profile_url sempre apunta a europarl.europa.eu/meps/en/{id}, i /meps/{mep_id} funciona correctament. El total ara és offset + items + 1-hint per indicar que hi ha més pàgines (abans retornava el limit com si fos el total — tens raó). coverage_complete: false per deixar clar que la paginació és oberta.
  3. Consultations — totes les dates en format ISO-8601 (YYYY-MM-DDTHH:MM:SSZ). El feedback_id sempre string.
  4. Legal-text — /legal-text/{celex}/recital-article-map ara captura l'excepció del TF-IDF i retorna 503 amb reason_code: computation_unavailable en comptes del 500 cru. Els dos endpoints POST (resolve-references i resolve-aliases) ara estan documentats com a READ-ONLY, idempotents, sense cap modificació de dades al servidor. Són POST només perquè el body pot ser llarg; cap risc d'escriptura.
  5. Commissioners — el parser de detail_url ara prioritza el link del títol i rebutja #, javascript: i mailto:. Fet amb test de regressió directe sobre el HTML de la Comissió.
  6. Default limit 20 → 50 a tots els endpoints paginats (tens raó sobre el col·lapse amb 20; 100 continua sent el màxim).
